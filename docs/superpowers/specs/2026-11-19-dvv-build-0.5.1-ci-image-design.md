# dvv-build 0.5.1: a prebuilt Linux CI image

Status: implemented in dvv-build 0.5.1 (tag v0.5.1). Design revision 3 (revision 2 approved 2026-11-19; revision 3 adds the errata of §14, which record every change made during the implementation). The user confirmed the four decisions in §10. Revision 1 was reviewed by an optimistic reviewer (A-I1,
A-M1..A-M9) and a pessimistic reviewer (B-I1..B-I3, B-M1..B-M10). §13 gives the response to each
finding.
Repository: dvv-build (0.5.0 → 0.5.1). The dependents pick it up by raising their dvv-build line.
Code is cited at dvv-build@e3a0ae4 (tag v0.5.0) unless another repository is named. External facts are
cited to the sources in §12. "Spec's call" marks a choice this spec makes without the user. §10 lists
the four decisions the user confirmed, each with its trade-off. §8 lists what must be verified on GitHub
before or during the implementation. Where this spec is not sure how GitHub Actions behaves, it says
so there and does not guess.

## 1. Intent

Every Linux job of the reusable workflow installs its toolchain from the Ubuntu mirrors on every run:

- `sudo apt-get update && sudo apt-get install -y clang-19 libclang-rt-19-dev libstdc++-14-dev`
  (dvv-ci.yml:281-283, the `&install-linux-compiler` anchor). It runs in prime-linux even when both
  caches hit, because the compiler's version is part of the wxWidgets key (dvv-ci.yml:280, :298).
  linux (:453) and tidy (:633) run it too.
- the window-system packages (dvv-ci.yml:319-321 in prime-linux, :456-458 in linux and tidy) and
  the Vulkan packages (dvv-ci.yml:460-463 in linux).
- `actions/setup-python` and `pip install -r tools/requirements.txt` in every job
  (dvv-ci.yml:131-137, used in all Linux jobs: :278-279, :450-451, :597-599, :629-631).

On 2026-11-18/19 the apt step hung for 12-21 minutes in prime-linux, linux-clang,
linux-clang-tsan, linux-clang-asan and tidy. The step has no timeout, so a hang lasts until the job
timeout (180 minutes, dvv-ci.yml:272, :437; tidy 150, :623). One PR run needed six reruns. Once the
step failed with exit 100 while `security.ubuntu.com` was mid-sync. On a normal day prime-linux takes
about 7.5 minutes, the Linux build and test jobs 2-5 minutes and tidy about 28 minutes (the brief's
evidence).

dvv-build 0.5.1 replaces all of those steps with one prebuilt image, and every Linux job runs inside
it. The image holds exactly the packages and tools that the jobs install today, and the environment
that setup-python exports. No Linux job reaches an Ubuntu mirror, the Python download or PyPI any
more. A dvv-build release pins its image by digest, so `dvv-ci.yml@v0.5.1` always means one exact
image.

The dvv rule binds the release (README.md:74-80): compatible means the same major and at least the
minimum, also for 0.x. 0.5.1 is compatible: a repository that raises its dvv-build line and its
`@v<X>` to 0.5.1 changes nothing else. The user's standing preference binds every choice: the cleanest
design and the best long-term solution, and the size of a change is never a reason against it.

## 2. Goals, non-goals, anti-goals

Goals:
1. No Linux job of dvv-ci.yml runs `apt-get`, `actions/setup-python` or `pip install`. The CI image
   replaces them.
2. Every job behaves as it does today, apart from where its tools come from. That means the same:
   - compiler, standard library and tool pins
   - Python environment variables
   - presets and tests
   - Xvfb display and lavapipe device

   The tests also run as a non-root user, as they do today. §8 V10 lists the container differences
   that remain, and each is either fixed or shown to be invisible to the tests.
3. One release means one image. dvv-ci.yml pins the image by digest. dvv-build's own CI fails when
   the pinned image is not the one published for that commit's inputs, or cannot be pulled
   anonymously.
4. The image is reproducible from its inputs. The Ubuntu packages come from a pinned archive
   snapshot and the base image is pinned by digest. So the image's package versions are a function
   of its inputs, and the Linux cache keys can use a hash of what the build sees (§5.7).
5. Any package install that is left in the workflow gets a step timeout and a retry, or is removed.
6. The PR records the speed-up as measured numbers, before and after. A decision rule applies to them
   (§7).

Non-goals:
- Windows and macOS jobs. They keep their runners and their tools. Their remaining package installs
  get a timeout and a retry, or are removed (§5.9).
- dvv-build's own `tools` job (ci.yml:22-68). It stays on the plain runners, so the script tests also
  run where a developer runs them (§5.10).
- rawreel's release workflow, which runs its own apt steps against the live mirrors (rawreel
  .github/workflows/release.yml:164, :168, :227-228). The consequence is that CI and the Linux release
  build stop using the same package builds. Today both take the newest noble-updates. From 0.5.1, CI
  uses the snapshot and the release uses the live mirror, so a noble-updates point release of
  clang-19 or libstdc++ could change a release build while CI stays green. A rawreel follow-up issue,
  opened with this release, moves the Linux release build into the same image (§9 step 6).
- arm64 images. CI is x86_64 only. The local arm64 image and its overrides (the arm64
  clang-tidy wheel with its four-part version, the arm64 stand-ins for Slang, FFmpeg and the
  validation layer) are prior art only.
- Moving the third-party prefix or wxWidgets into the image. They stay in the Actions cache, keyed as
  today plus the image environment (§5.7).
- A floating "latest toolchain" (§10 Q4). Today apt picks the newest noble-updates build on every
  run. The image freezes it at its snapshot. A newer clang-19 or Mesa arrives with a new snapshot,
  which means a new image and a new dvv-build patch release.

Anti-goals (each would be a failure even if it worked):
- Tests that run as root in CI. Root ignores file permissions, so the permission tests return early
  and pass without checking anything: dvv-base tests/test_split_file_sink.cpp:632-634, :643-645,
  :681 and rawreel tests/test_recent.cpp:191 all branch on `geteuid() == 0`. A green run would then
  prove less than today's.
- An image tag in dvv-ci.yml instead of a digest, or a tag that is moved.
- A silent drift between the image and the dvv-build that uses it. Each of these must fail loudly:
  - a recipe, package list or tool pin that changed without a new image
  - an image whose tools differ from the pins
  - a pinned digest that is not the published image of those inputs
- A second, host-based code path kept "just in case" (an apt fallback). It would bring back the
  unreliable path and give two environments to keep identical (§5.8, §10 Q3).
- Cache entries built on the host restored into the container, or the other way round (§5.7).
- A change that forces any calling repository to edit anything except its dvv-build line and
  `@v<X>`. Examples: new `permissions:`, credentials or repository variables.

## 3. Constraints

- **Reusable-workflow layouts.** dvv-ci.yml serves three layouts: lib, app and self
  (dvv-ci.yml:1-12, :42-48).
  - lib: dvv-build is checked out at `job.workflow_sha` (dvv-ci.yml:122-130), so the dvv-build in
    use is the commit of the called workflow.
  - app: `DVV_BUILD` is the app's pinned `libs/dvv-build` (dvv-ci.yml:47), and check-pins requires
    `@v<X>` to equal it (dvv-ci.yml:609-615).
  - self: `DVV_BUILD` is the dvv-build checkout itself.
- **Caller permissions and the registry login.** The callers grant only `contents: read` at the top
  level (dvv-base .github/workflows/ci.yml:9-10; rawreel .github/workflows/ci.yml:14-15). dvv-ci.yml
  declares the same (dvv-ci.yml:39-40). A called workflow cannot be granted more than the caller
  grants.

  The pull is **not** anonymous. On GitHub-hosted runners, when a job container's registry is
  ghcr.io and the job gives no credentials, the runner logs in with `github.actor` and the job's
  `GITHUB_TOKEN` ([runner] ContainerOperationProvider.cs:193, :520-535). It tries that login three
  times and fails the job if all three fail (:471-499). Here that token is the caller's token, with
  `packages: none`; for forks and Dependabot it is a read-only token.

  So the image must be pullable by a token without package scope, which means a public package
  (§5.3, V3). It also means that a pull by dvv-build's own CI proves nothing about visibility: its
  token belongs to the linked repository. §5.10 adds an explicit anonymous check.
- **Contexts for `jobs.<id>.container`.** Only `github`, `needs`, `strategy`, `matrix`, `vars` and
  `inputs` are available; `env`, `job` and `runner` are not ([GH-contexts], the rows
  `jobs.<job_id>.container` and `.container.image`). The expression language has no lower-case
  function ([GH-expr]). Image names must be lower case, and the owner login has capitals (rawreel
  ci.yml:19). So the image reference, and the user, are computed in a step and passed through
  `needs`.
- **Container jobs run on Linux runners only** ([GH-syntax]). `--network` and `--entrypoint` are not
  supported in `container.options` ([GH-container], "Setting container resource options").
- **The default `run` shell differs.** Inside a container the default shell is `sh`, not bash
  ([GH-container], Overview note). On the host the unspecified shell is `bash -e {0}`. An explicit
  `shell: bash` is `bash --noprofile --norc -eo pipefail {0}` ([GH-syntax], the shell table).
- **Docker user.** GitHub's Dockerfile guidance says not to use `USER` ([GH-dockerfile], USER). That
  page is about Docker actions. For job containers this spec sets the user in `container.options`,
  and verifies the result (V1).
- **What setup-python exports today.** On every Linux job, setup-python sets `pythonLocation`,
  `PKG_CONFIG_PATH=<install>/lib/pkgconfig`, `Python_ROOT_DIR`, `Python2_ROOT_DIR` and
  `Python3_ROOT_DIR` (all `<install>`). It prepends `<install>/lib` to `LD_LIBRARY_PATH` and adds
  `<install>` and `<install>/bin` to PATH ([setup-python] src/find-python.ts:151-174). The image
  must set the same environment (§5.2).
- **Tool pins.** tools/requirements.txt:2-5 (`cmake==4.3.2`, `ninja==1.13.2`,
  `clang-format==19.1.7`, `clang-tidy==19.1.0`). Python 3.13 (dvv-ci.yml:134). The compiler is
  clang-19 with libstdc++-14 from Ubuntu noble (dvv-ci.yml:283; README.md:173-180). The presets name
  `clang++-19` (cmake/DvvPresets.json:38).
- **Repo policy.** One squashed commit per pull request, and the user merges. Every dependency pin is
  on a tag. A pushed tag is never moved (README.md:80). README and release notes state facts only,
  with no machine paths, real names or e-mail addresses.

## 4. Approaches considered

**A. A prebuilt image, used through `jobs.<id>.container` (chosen).** One image holds the packages,
the tools and the Python environment. GitHub's runner pulls it, starts it, and runs every step and
every JavaScript action inside it. The workspace is mounted at `/__w`.

What it gives:
- It removes all apt and pip traffic and all install time from the jobs.
- It is GitHub's documented mechanism, so `uses:` actions (checkout, cache) keep working unchanged.
- The runner controls cancellation and timeouts.
- It makes the environment content-addressed: one digest per release.

What it costs:
- The image pull becomes a new network step, though from GitHub's own registry (§5.8).
- The workspace path changes, which affects the caches (§5.7).
- Root is the default user, the shell is `sh`, and Docker's isolation applies. §5.4 and §5.5 handle
  each.
- Every Linux job pulls the image, which may slow the light jobs. §7 sets a rule for that.

**B. A cache of the `.deb` files.** Keep the host runner. Restore `/var/cache/apt/archives` (and the
apt lists) from actions/cache, then run `apt-get install` from it.

What it gives: the same host and user as today, and no container caveats.

What it costs:
- The install steps stay, and unpacking clang and GTK still takes time on every job.
- `apt-get update` is still needed unless the lists are cached too. Cached lists go stale, and a
  mirror that dropped an old build returns 404, which is today's failure in a new form.
- When the cache is evicted, the install falls back to the network.
- Each repository fills its own copy.

It halves the problem and adds a second cache to maintain. Rejected.

**C. Retries only.** Give the apt steps `timeout-minutes`, `Acquire::Retries` and a retry loop. That
turns a 3-hour hang into a few lost minutes. It keeps the install cost on every job and the dependence
on mirror sync. It is the right tool for the image build (§5.3) and for the package installs that are
left (§5.9), and the wrong tool for the main problem. Rejected as the main approach.

**D. The image run from the steps (`docker run`/`docker exec` as a custom `shell:`).** It would keep
the host's paths and user, and it would allow a timed `docker pull` with retries in a step. It fails
on three points:
- The step environment (`env:`, `GITHUB_ENV`, `GITHUB_OUTPUT`) lives in the host process and must be
  forwarded by hand, except PATH and HOME.
- A step timeout or a cancellation kills the `docker exec` client but not the process inside.
- It is an undocumented pattern built from a wrapper script.

Rejected: it trades documented behaviour for a fragile wrapper.

**E. A custom runner image (GitHub larger runners or self-hosted).** It is the cleanest environment
if it is available, but it needs paid larger runners or self-hosted machines. It is out of scope for
these public repositories on the standard hosted runners; this spec claims no more than that about
its availability. Rejected.

## 5. Design

### 5.1 Files

New in dvv-build:
- `ci-image/Dockerfile`: the image (§5.2). Every setting that changes the image's content, labels or
  metadata is written here (§5.3).
- `ci-image/packages.txt`: the Ubuntu packages, one per line, in commented groups. This is the only
  list. The Dockerfile reads it, and the check (§5.6) verifies that each package is installed.
- `ci-image/build.sh`: the one build command, with its fixed buildx options (compression, provenance,
  push by digest). ci-image.yml calls it and holds no build option of its own.
- `tools/ci-image-inputs.cmake`: prints `hash=<64 hex digits>`, the **inputs hash**. It is the
  SHA-256 over the sorted list of the inputs, each written as `<path>\n<sha256 of the file>\n`. The
  inputs are every tracked file under `ci-image/`, plus `tools/requirements.txt`, plus this script
  itself, plus `.github/workflows/ci-image.yml` (the workflow decides how the image is built, so an
  edit to it alone must not reuse a tag; erratum 8). The output contract is the same as tools/separate-prefix-hash.cmake, whose output the key
  step already parses (dvv-ci.yml:291-296).
- `tools/check-ci-image.cmake`: the in-job check (§5.6). It is not an input: it only checks the image
  and builds nothing into it.
- `.github/workflows/ci-image.yml`: publishes the image (§5.3).
- Tests: `tests/ci/test_ci_image_inputs.cmake`, `tests/ci/test_check_ci_image.cmake` and
  `tests/ci/test_sanitizers.cmake`, with two small sources (§6).

Changed:
- `.github/workflows/dvv-ci.yml` (§5.4-§5.9, §5.11).
- `.github/workflows/ci.yml`: the new tests, the pin check and the install timeout (§5.9, §5.10).
- `README.md` "CI" and `CHANGELOG.md` [0.5.1].

### 5.2 Image contents

```dockerfile
# The CI image of the dvv Linux jobs (dvv-ci.yml). Inputs: everything in ci-image/, plus
# tools/requirements.txt and tools/ci-image-inputs.cmake. Published by ci-image.yml through build.sh.
FROM ubuntu:24.04@sha256:<digest of the noble image at the snapshot date>
# The Ubuntu archive as of this moment (snapshot.ubuntu.com): the inputs fix every package version.
ARG UBUNTU_SNAPSHOT=<YYYYMMDDTHHMMSSZ>
# The Python build that actions/setup-python installs (actions/python-versions).
ARG PYTHON_VERSION=3.13.<n>
ARG PYTHON_URL=<download_url of that build in versions-manifest.json (linux, 24.04, x64)>
ARG PYTHON_SHA256=<sha256 of python-<version>-linux-24.04-x64.tar.gz>
# The pip that setup.sh's own upgrade installs: the version ensurepip bundles with PYTHON_VERSION.
ARG PIP_VERSION=<pip version bundled with PYTHON_VERSION>
ARG DVV_CI_IMAGE_INPUTS
ARG DVV_CI_IMAGE_SOURCE
LABEL dvv.ci-image.inputs=$DVV_CI_IMAGE_INPUTS org.opencontainers.image.source=$DVV_CI_IMAGE_SOURCE
ENV DEBIAN_FRONTEND=noninteractive LANG=C.UTF-8
COPY ci-image/packages.txt tools/requirements.txt /tmp/dvv-ci-image/
# One RUN per group of packages.txt (base, compiler, GUI, display and Vulkan), so they become
# separate layers that download in parallel. Each runs apt from the snapshot with
# -o Acquire::Retries=5 and installs the group with recommends, as `apt-get install -y` does today.
RUN <group 1> ...
RUN <group n>; record `dpkg-query -W` into /etc/dvv-ci-image/packages.lock; delete the apt lists
# Python: a `download` stage on the same base installs curl from the snapshot, downloads PYTHON_URL
# with curl --retry 5 --retry-all-errors and checks the SHA256; curl stays out of the final image.
# The final stage runs the archive's own setup.sh with RUNNER_TOOL_CACHE=/opt/hostedtoolcache (the
# python link, ensurepip), exactly as setup-python installs it, and with
# PIP_CONSTRAINT=<a file holding pip==$PIP_VERSION>, so setup.sh's `pip install --upgrade
# --force-reinstall pip` installs that pinned pip and not PyPI's newest. The build fails unless
# `python -m pip --version` reports PIP_VERSION. Then `pip install --no-cache-dir --retries 10
# --timeout 60 -r requirements.txt` and record `pip freeze --all` (pip included) into
# /etc/dvv-ci-image/pip.lock.
RUN <python> ...
# The environment setup-python exports today (find-python.ts:151-174), with
# <install> = /opt/hostedtoolcache/Python/<version>/x64:
ENV pythonLocation=<install> Python_ROOT_DIR=<install> Python2_ROOT_DIR=<install> \
    Python3_ROOT_DIR=<install> PKG_CONFIG_PATH=<install>/lib/pkgconfig \
    LD_LIBRARY_PATH=<install>/lib PATH=<install>/bin:<install>:$PATH
RUN groupadd --gid 1001 runner && useradd --uid 1001 --gid 1001 --create-home runner \
 && mkdir -m 1777 /tmp/.X11-unix \
 && printf '%s\n' "$DVV_CI_IMAGE_INPUTS" > /etc/dvv-ci-image/inputs.sha256 \
 && cat /etc/dvv-ci-image/packages.lock /etc/dvv-ci-image/pip.lock | sha256sum | cut -c1-64 \
      > /etc/dvv-ci-image/environment.sha256
# No USER and no WORKDIR (GitHub's Dockerfile guidance); the job sets the user (dvv-ci.yml).
```

Further lines may follow from V10 (for example an `/etc/machine-id`), each with the difference it
removes.

`ci-image/packages.txt` lists exactly today's packages, plus only the base tools that a bare
`ubuntu:24.04` lacks and the jobs use:

| Group | Packages | Why |
|---|---|---|
| Base | ca-certificates git perl zstd binutils | listed below |
| Compiler | clang-19 libclang-rt-19-dev libstdc++-14-dev | dvv-ci.yml:283 |
| Window system and GUI | libgtk-3-dev pkgconf libx11-dev libxcb1-dev libxrandr-dev libwayland-dev zlib1g-dev libpng-dev | dvv-ci.yml:321, :458 |
| Display and Vulkan | xvfb xauth mesa-vulkan-drivers libvulkan1 vulkan-tools | dvv-ci.yml:458, :462 |

Why each base package is there:
- `ca-certificates`: bootstrap's HTTPS downloads.
- `git` (2.18 or newer):
  - Without it, actions/checkout falls back to a REST download with no submodules and no history.
    App layout needs the submodules (dvv-ci.yml:121), and lint needs the full history (:594).
  - fetch-deps clones with git.
  - DvvDeps calls `find_program(GIT_EXECUTABLE git REQUIRED)`.
- `perl`: `shasum -a 256` in `&keys-unix` (dvv-ci.yml:304, :310). It is in `perl`, not in the
  `perl-base` that a bare image has. It is listed so that it does not depend on git's dependencies.
- `zstd`: actions/cache compresses with zstd when it is present, and the compression method is part
  of the cache version (§5.7).
- `binutils`: `readelf` is the fallback of `find_program(DVV_READELF NAMES llvm-readelf-19
  llvm-readelf readelf REQUIRED)`, and the validation-layer post-install calls `strip`.

No other runner-image tool is added without a consumer. The cold prime (T5) and the dependents' test
runs (T6) show any that is missing.

Recommends stay in. Today's `apt-get install -y` installs them, and `llvm-readelf-19` comes that way
(clang-19 recommends llvm-19-dev). wxWidgets cannot pick up a stray library: its GTK build switches
every optional dependency explicitly (deps/versions.cmake:344-355).

Spec's calls in the image:
- **The Python build** is the one setup-python gives today (actions/python-versions). It is installed
  by its own setup script at the tool-cache path, with the same exported environment. Deadsnakes
  would be a second Python build with no benefit. The runner mounts its own tool cache at `/__t`, not
  at `/opt/hostedtoolcache` (§8 V7), so nothing hides the image's copy.
- **No virtual environment.** Today pip installs into the setup-python interpreter (dvv-ci.yml:137),
  and the image does the same.
- **pip is pinned.** setup.sh upgrades pip from PyPI without a version (actions/python-versions
  installers/nix-setup-template.sh), which would make the image depend on the build date. A
  constraint pins that upgrade to the pip that ensurepip bundles with `PYTHON_VERSION`, so pip is a
  function of the inputs and needs no separate lookup. `pip freeze --all` puts pip into pip.lock and so
  into the environment hash. The pip version is invisible to the jobs: they never run pip.
- **The tools are root-owned and read-only** for the job user. The job never installs anything
  (§5.6).
- **The user `runner` (1001:1001)** gives the usual hosted-runner uid a passwd entry, because some
  libraries look the user up. The job's actual uid and gid come from the host (§5.4).
- **`HOME`** is `/github/home`, which the runner sets for container jobs, mounted from the host's
  `_temp/_github_home` and owned by the runner account ([runner] ContainerOperationProvider.cs:310-314).
- **`LANG=C.UTF-8`**, as on the runner host. A bare ubuntu:24.04 has no LANG.
- **`/tmp/.X11-unix`** has mode 1777, because a non-root Xvfb cannot create it in the right mode.

What stays out: the third-party prefix, wxWidgets and the downloaded archives. They depend on
`deps/**` and stay in the Actions cache as today (dvv-ci.yml:89-108).

### 5.3 Registry, name, build and publish

**Registry and name.** The image is `ghcr.io/<owner>/dvv-build-ci`, linked to the dvv-build
repository through `org.opencontainers.image.source` ([GHCR], "Labelling container images"). The
source URL is a build argument, so no committed file names the owner.

**Visibility: public** (§10 Q1).
- Every job's implicit login uses the caller's token without package scope (§3). A private package
  would need `packages: read` and a per-repository grant for every caller.
- A first publish is private by default ([GHCR]). Making it public is a one-time manual step.
- dvv-build's CI enforces it: the pin check (§5.10) fails until an anonymous pull of the pinned digest
  works, so a private image can never be merged or released.
- [GHCR-access] confirms that public container packages can be pulled anonymously. The authenticated
  pull with a token that has no package scope is V3.

**`ci-image.yml`** holds triggers and plumbing only:
- `permissions: contents: read, packages: write`.
- `concurrency: { group: ci-image, cancel-in-progress: false }`, so that two runs in the repository
  never build at the same time.
- Trigger: `push` to any branch, with a path filter on everything under `ci-image/`,
  `tools/requirements.txt`, `tools/ci-image-inputs.cmake`, `tools/check-ci-image.cmake` and the
  workflow itself (`branches: ['**']`, so a tag push never runs it). Also `workflow_dispatch`. There is no tag trigger: nothing pulls by a release
  tag, and the digest in dvv-ci.yml is the release's name for its image.

Its steps:
1. Compute the inputs hash `<h>`, with the pinned tools installed as in the `tools` job.
2. Look up `ghcr.io/<owner>/dvv-build-ci:inputs-<first 16 of h>` with
   `docker buildx imagetools inspect`.
   - The tag exists: print its digest and stop.
   - Only the logged-in `<ref>: not found` counts as absent: go on.
   - Any other error fails the run, so a transient registry error never looks like an absent tag.
3. Build with `ci-image/build.sh`, retried up to three times. The script uses
   `docker buildx build --provenance=false` with the chosen layer compression (V13), and the
   `DVV_CI_IMAGE_INPUTS` and `DVV_CI_IMAGE_SOURCE` build arguments. It loads the image locally.
4. Run the full check on the local image before anything is pushed (T3, §6).
5. Push by digest only (`push-by-digest=true`, no tag), with three attempts.
6. Look up the tag again. If it is still absent, add it with
   `docker buildx imagetools create --prefer-index=false --tag …:inputs-<h16> …@<digest>`. Without
   `--prefer-index=false`, a single source is wrapped in a new image index whose digest differs from
   the pushed manifest, so the tag would never name the pinned digest. The tag's digest is then
   inspected and must equal `<digest>`. If the tag now exists on another digest, the run fails and
   leaves its own push untagged.
7. Write the digest into the job summary.

So one inputs hash maps to one tagged digest, and a tag is never moved. The README says that versions
tagged `inputs-*` are never deleted, because releases pin them. Untagged versions are left over from a
lost race or a failed run, and may be cleaned up.

**Digest pinning.** dvv-ci.yml's workflow-level env gets one line,
`DVV_CI_IMAGE: dvv-build-ci@sha256:<64 hex digits>`, next to the existing env (dvv-ci.yml:42-48). It is
the only place the digest is written, and nothing ever pulls by tag. `@v0.5.1` therefore means the
digest that dvv-ci.yml holds at tag v0.5.1.

**Attestations.** Spec's call: none in 0.5.1. A build-provenance attestation can be added later
without a change for the callers.

**Changing the image** inside a dvv-build PR takes two commits on a branch of the dvv-build
repository itself:
1. Commit 1 changes an input. ci-image.yml publishes `inputs-<h>` and prints the digest.
2. Commit 2 writes that digest into `DVV_CI_IMAGE`.

Until commit 2, the pin check and the self CI fail ("built from inputs X, this dvv-build has Y"). The
squash merge leaves one commit.

A PR from a fork cannot publish to the upstream registry. The maintainer pushes the fork's branch to
the upstream repository, and the two-commit flow runs there.

### 5.4 How the Linux jobs use the image

The jobs that move into the image are prime-linux (dvv-ci.yml:269), linux (:433) and tidy (:619). lint (:585) stays on
the host (§14 erratum 9). dvv-build-min (:55) stays on the host. It installs nothing, it runs on the same runner
image, and it computes the image reference and the user that the other jobs need.

**dvv-build-min** gets the outputs `image` and `user`, from one step that always runs:

```yaml
      - name: CI image
        id: image
        shell: bash
        env:
          # The dvv-build whose workflow runs owns the image. A fork of dvv-build that runs its own CI
          # sets the repository variable DVV_CI_IMAGE_OWNER to the upstream account; the digest pins
          # the content wherever it is pulled from.
          OWNER: ${{ vars.DVV_CI_IMAGE_OWNER || job.workflow_repository || github.repository }}
        run: |
          owner=${OWNER%%/*}
          echo "image=ghcr.io/${owner,,}/$DVV_CI_IMAGE" >> "$GITHUB_OUTPUT"
          # The runner account of this runner image: the container runs as it (no root).
          echo "user=$(id -u):$(id -g)" >> "$GITHUB_OUTPUT"
```

Notes on these inputs:
- `job.workflow_repository` is available in steps ([GH-contexts], the job context's workflow
  identity properties). It names the dvv-build that defines the running workflow. So a fork of a
  dvv library that calls the upstream dvv-build pulls the upstream public image.
- `vars` is the caller's context. Only a fork of dvv-build itself needs the variable, for its own
  self CI. No dvv repository sets it.

**The container block** is one YAML anchor on prime-linux, reused by linux and tidy:

```yaml
    container: &linux-container
      image: ${{ needs.dvv-build-min.outputs.image }}
      # The runner account's uid:gid (tests must not run as root); tini reaps orphans as the host's
      # init does; the host's IPC namespace and /dev/shm; no seccomp filter, as on the host (TSan's
      # personality(ADDR_NO_RANDOMIZE) re-exec).
      options: >-
        --user ${{ needs.dvv-build-min.outputs.user }}
        --init --ipc=host --security-opt seccomp=unconfined
    defaults: &linux-defaults
      run:
        shell: bash -e {0}
```

Each consequence of `container:`, and what the design does about it:

- **Root (the default user).** Root changes what the tests check (§2 anti-goal). `--user` runs every
  step as the host runner account's uid and gid, taken from the same runner image, not guessed. Files
  created in the container therefore keep the host's owner and group.
  - The check step (§5.6) fails unless `id -u` is non-zero and equals the owner of
    `$GITHUB_WORKSPACE`.
  - Whether checkout, cache and the runner's file-command mounts work under `--user` is V1.
  - If V1 fails, the fallback is root for the actions, with the test steps run through
    `setpriv --reuid=<uid> --regid=<gid> --clear-groups`. That fallback would need a revision of this
    spec.
- **`sudo`.** No step uses it any more. All three `sudo apt-get` steps are deleted (dvv-ci.yml:281-283,
  :319-321, :456-463). The Vulkan step keeps only its check line (§5.6). The image has no sudo.
  bootstrap's "missing packages" hint (bootstrap.sh:74-75) is developer advice and stays.
- **Default shell.** The block restores the host's `bash -e {0}`. A plain `shell: bash` would add
  `pipefail` to steps that do not ask for it. Steps that name a shell keep it (dvv-ci.yml:286, :649).
  A workflow-level default would also change Windows' `run` steps, so the default is set per job.
- **`$GITHUB_WORKSPACE`.** It becomes `/__w/<repo>/<repo>`.
  - The Linux steps already use the variables `$GITHUB_WORKSPACE` and `$RUNNER_TEMP`
    (dvv-ci.yml:657-660).
  - No Linux step uses `${{ github.workspace }}` or `${{ runner.temp }}`, which may expand to host
    paths in a container job (V5). Their only uses are in the macOS jobs (dvv-ci.yml:526, :534) and
    in ci.yml's host `tools` job.
  - The README states the rule for future Linux steps.
  - `working-directory: ${{ inputs.repo }}` is relative and unchanged.
- **Actions inside the container.** checkout and cache are JavaScript actions. The runner runs them
  in the job container with its own Node. That needs glibc (in ubuntu:24.04) and git, plus GNU tar
  and zstd for the cache.
- **`hashFiles()`** in `PREFIX_HASH` (dvv-ci.yml:289) must hash the same files in a container job
  (V6).
- **setup-python and "Install tools".** Both leave the Linux jobs. The image provides the same
  interpreter, pins and exported environment (§5.2). The anchors `*setup-python` and `*install-tools`
  stay for Windows and macOS, and the Linux jobs use `*check-ci-image` (§5.6) in their place.
- **`--init`.** The runner keeps the container alive with `tail -f /dev/null` as its command.
  Without an init, orphans become zombies that nothing reaps. A test that probes whether a child is
  gone would then see it alive. On the host, init reaps them. `--init` puts tini in front of the
  command (V8).
- **`--ipc=host`.** Docker's default `/dev/shm` is 64 MB. Xvfb, GTK and lavapipe's X11 presentation
  use shared memory, and the host has no such limit.
- **Matrix and timeouts.** Unchanged: the same three matrix entries (dvv-ci.yml:443-446) and the same
  `timeout-minutes`.

The new step lists, per job:
- prime-linux: checkout, dvv-build checkout, check-ci-image, keys, lookups, restores, Bootstrap and
  saves. The "window-system packages" step (:319-321) is gone.
- linux: checkout, dvv-build checkout, check-ci-image, fetch-deps, the Vulkan check, keys, restores,
  Bootstrap, and Build and test.
- lint (on the host, §14 erratum 9): checkout, dvv-build checkout, setup-python, install-tools, then the four lint steps as today.
- tidy: as linux, without the Vulkan check, and with its Build and Tidy steps.

Lint moves into the image too (spec's call, subject to the §7 rule). It has no apt step, but its
setup-python plus a PyPI install (dvv-ci.yml:597-599) is the same kind of network dependency. In the
image, clang-format is the pinned one by construction.

### 5.5 Sanitizers in the container

- **ASan and LSan.** LeakSanitizer stops the world with ptrace on its own threads.
  - Docker's default seccomp profile allows `ptrace` from kernel 4.8 on ([moby-seccomp]
    default.json:430-434), and the profile is off here anyway.
  - The tracer has the same uid as the traced process, as on the host today, so no `CAP_SYS_PTRACE`
    is needed.
  - Docker's `docker-default` AppArmor profile still applies. It allows ptrace between processes
    under the same profile, which is the LSan case. V2 and T7 confirm it.
- **TSan.**
  - The hosted Ubuntu images set `vm.mmap_rnd_bits=28` ([runner-images]
    configure-environment.sh:56-57, issue 9491). That is a kernel setting, so the container sees it
    too, and TSan maps its shadow as on the host.
  - If a future image raised it, clang 19's TSan would re-exec itself under
    `personality(ADDR_NO_RANDOMIZE)`.
  - Docker's default seccomp profile allows `personality` only for the values 0, 8, 131072, 131080
    and 4294967295 ([moby-seccomp] default.json:855-913). ADDR_NO_RANDOMIZE (0x0040000) is not one
    of them.
  - `--security-opt seccomp=unconfined` removes the filter, so the re-exec works as on the host.
    That is the only claim: no seccomp filter, as on the host. AppArmor, the masked `/proc` paths
    and the reduced capability set stay, and V10 lists what a test could see of them.
- **Exact options:** `--user <uid>:<gid> --init --ipc=host --ulimit core=0:-1 --security-opt seccomp=unconfined`, the
  same on every Linux container job through one anchor. Spec's call: one environment for all Linux
  jobs, with no variants per sanitizer.
- **Verification:** T7 (§6) runs in dvv-build's self CI, in linux-clang-asan and linux-clang-tsan
  (`if: env.DVV_LAYOUT == 'self'`).
  - It prints (`unreadable` for a file it cannot read) `/proc/sys/vm/mmap_rnd_bits` and `/proc/sys/kernel/yama/ptrace_scope`.
  - It compiles a leak and a data race with clang++-19 and runs them.
  - The leak must exit non-zero with "detected memory leaks".
  - The race must report "WARNING: ThreadSanitizer: data race", and nothing matching
    "FATAL: ThreadSanitizer" or "unexpected memory mapping".

  After that, the dependents' asan and tsan suites (§9) are the real proof.

### 5.6 The in-job check: "Check the CI image"

A step on every Linux container job, right after the dvv-build checkout (anchor `&check-ci-image`):

```yaml
      - &check-ci-image
        name: Check the CI image
        run: cmake "-DDVV_BUILD=$DVV_BUILD" -P "$DVV_BUILD/tools/check-ci-image.cmake"
```

`tools/check-ci-image.cmake` checks five things and fails with one message per mismatch:
1. **Inputs.** `/etc/dvv-ci-image/inputs.sha256` equals `tools/ci-image-inputs.cmake` run on
   `$DVV_BUILD`. This proves the pinned image was built from this dvv-build's inputs.
   - In lib and self layouts, `DVV_BUILD` is the workflow's own commit (dvv-ci.yml:129).
   - In app layout, check-pins requires the pinned dvv-build to be the called one
     (dvv-ci.yml:609-615).
   - So a mismatch means an unpinned image or an inconsistent app branch, and either should fail.
2. **User.** `id -u` is not 0 and equals the owner uid of `$GITHUB_WORKSPACE` (§5.4).
3. **Tools.** Each `name==version` line of `$DVV_BUILD/tools/requirements.txt` matches the installed
   tool:
   - `cmake --version` (first line `cmake version 4.3.2`)
   - the four wheel tools: `python -m pip show <name>` reports the pinned `Version:` exactly; their
     `--version` is only an entry-point check (ninja's passes as `<pin>` or `<pin>.git.…`)
   - `python --version` is 3.13.x, and `Python3_ROOT_DIR`, `pythonLocation` and `PKG_CONFIG_PATH`
     name its install directory
4. **Compiler and packages.** `clang-19 --version` reports major 19, and
   `dpkg-query -W -f='${Status}' <pkg>` is "install ok installed" for every line of
   `ci-image/packages.txt`. libstdc++ 14 is checked where it is checked today
   (DvvCompilerOptions.cmake).
5. **Report.** It prints, in a collapsed group:
   - the user, as `user <uid>:<gid> (workspace owner <uid>)`
   - packages.lock and pip.lock
   - the inputs and environment hashes
   - the image reference, when `DVV_CI_IMAGE` is set; the digest is also in the job's "Initialize
     containers" log

   So every run's log records the exact versions it used.

The whole check runs on every Linux job (spec's call; A-M3 not applied, §13). Items 1, 2 and 5 are
what callers need. Items 3 and 4 cost about a second, and they guard every job against an image
that does not match its own lock files. With them there is one check mode and one set of T2 cases
instead of two.

The Vulkan step becomes `cmake -P "$DVV_BUILD/tools/check-vulkan-device.cmake"` alone (it was
dvv-ci.yml:460-463), with the comment changed from "Vulkan 1.4 from noble-updates" to "from the CI
image". check-vulkan-device finds `vulkaninfo` on PATH (check-vulkan-device.cmake:52-58). lavapipe
needs no device nodes, so the container needs no `--device` option.

### 5.7 Xvfb, lavapipe, and the caches

**Xvfb and lavapipe.** "Build and test" runs as today:
- the command is
  `xvfb-run -a -s "-screen 0 1920x1080x24" cmake --workflow --preset …`
- the environment is `DVV_REQUIRE_GPU=1`, `DVV_VK_VALIDATION=sync`, `DVV_VK_VALIDATION_REQUIRED=1`
  and `NO_AT_BRIDGE=1` (dvv-ci.yml:474-483).

Xvfb runs as the runner uid in the pre-made `/tmp/.X11-unix`. lavapipe and Mesa's device_select layer
come from the image at the same Ubuntu paths. So DVV_KEEP_LOADED, the 0.4.2 LD_PRELOAD helper
(CHANGELOG.md:41-64), finds them as before. GTK finds its fonts through libgtk-3-dev's fontconfig
and font dependencies (V10 compares `fc-list`).

**Cache paths stay, and the keys change.** The cache paths are relative
(`${{ env.DVV_ROOT }}/_third_party/…`, dvv-ci.yml:186, :194, :237). In the container they resolve
under `/__w` with unchanged path strings, and zstd in the image keeps the same compression method.
So without a key change, a container job would restore the entries the host jobs saved. That is
wrong:
- The prefix embeds its absolute install path. A local prefix has it in the pkg-config files,
  wx-config and `wx/setup.h` (`#define wxINSTALL_PREFIX "<absolute prefix>"`). The CMake package
  files carry none.
- That path is under the runner's `work` directory on the host and under `/__w` in the container.

The Linux `wx` and `prefix` keys therefore gain the image's **environment hash**:
`/etc/dvv-ci-image/environment.sha256`, the SHA-256 of packages.lock and pip.lock (§5.2). That is a
hash of what a build can see: every Ubuntu package version, the Python build and the Python tools.
The pinned snapshot and base digest make it a function of the inputs, so it is as deterministic as
the inputs hash. It differs from the inputs hash in one way: a recipe change that leaves every
version alone keeps it. In `&keys-unix` on Linux (dvv-ci.yml:297-306), with
`env=$(cut -c1-16 /etc/dvv-ci-image/environment.sha256)`:

```
wx=wx-Linux-clang-<wx hash 16>-<compiler 16>-<env 16>
prefix=third-party-Linux-clang-<PREFIX_HASH>-<env 16>
downloads=downloads-Linux-<pins>            (unchanged: archives do not depend on the path)
```

Effects:
- The first run of each repository after it adopts 0.5.1 is a cold prime. wxWidgets and the prefix
  are built once, and the downloads are restored, so nothing new is downloaded.
- After that, sharing between jobs works as today. prime-linux saves, and linux and tidy restore the
  same key with the same path and compression, so the same cache version (V12).
- A new snapshot or a new pin builds new entries. Without that, a change of the GTK development
  packages would never rebuild wxWidgets, a gap in today's keys.
- A comment, a build flag or a label in `ci-image/` makes a new image but keeps the caches.
- The wx key's compiler fingerprint becomes redundant on Linux. It stays, because the anchor is shared
  with macOS.
- Branch scoping is unchanged, and the macOS branch of `&keys-unix` is unchanged.

### 5.8 Fallback and robustness

- **The pull is the only new network step.** Checkout, cache, fetch-deps and bootstrap's downloads
  on a prime miss stay as they are today, with their retries (bootstrap.sh:170-185). The Ubuntu
  mirrors and PyPI leave the Linux jobs entirely.
- **What the runner does.**
  - It logs in to ghcr.io (three attempts) and then pulls with three attempts, with a random 1-10
    second pause between them ([runner] ContainerOperationProvider.cs:198-226). It logs "Docker
    pull failed with exit code …, back off … seconds before retry".
  - A failed login or pull fails the job in "Initialize containers", before any step, and the run is
    rerun. A registry error that lasts longer than about 20 seconds therefore fails the job.
- **A hung pull.** No workflow step can wrap container initialization with a timeout, so a hung pull
  is bounded only by the job timeout. That is the one hang mode left. It needs a stalled transfer
  from GitHub's own registry, not a third-party mirror in sync.
- **No fallback path** (§2 anti-goal, §10 Q3). A host-plus-apt fallback behind a repository variable
  (like `DVV_MACOS_SOFTWARE_GPU`, dvv-ci.yml:512-519) would keep the apt steps alive in dvv-ci.yml,
  untested on every normal run. A GHCR outage is a GitHub outage, and checkout and the cache already
  depend on GitHub.
- **The image build** uses four networks: Docker Hub, snapshot.ubuntu.com, the python-versions
  release and PyPI. Each has retries (§5.2), and the build itself is retried three times (§5.3). A
  failure there delays a new image, but no CI run.

### 5.9 The package installs that are left (not Linux)

- **"Install tools" (pip)** on Windows and macOS (dvv-ci.yml:135-137) gets `timeout-minutes: 15` and
  becomes `python -m pip install --retries 10 --timeout 60 -r …`. pip retries connection errors and
  timeouts per request, and the step timeout bounds a stall. ci.yml's `tools` job gets the same
  (ci.yml:37-38).
- **`brew install ninja` is deleted** (dvv-ci.yml:361, :510). On macOS, `*setup-python` and
  `*install-tools` run first (dvv-ci.yml:336-339, :501-502), and they install the pinned
  `ninja==1.13.2` (tools/requirements.txt:3). setup-python puts the interpreter's bin ahead of
  Homebrew on PATH (find-python.ts:173-174). bootstrap only needs `command -v ninja`
  (bootstrap.sh:55-59). So the brew install was shadowed, and it is one network install fewer. V14
  confirms `command -v ninja` and `ninja --version` on the macOS runner.
- **setup-python** on Windows and macOS stays. The runner images carry 3.13 in their tool cache.
- `brew install mesa` keeps its three attempts and its 20-minute step timeout (dvv-ci.yml:521-527).

### 5.10 dvv-build's own CI

- **self** (ci.yml:70-73) calls dvv-ci.yml. So dvv-build's own prime-linux and linux matrix run in the
  image, with the check (§5.6) and the canaries (§5.5).
- **tools** (ci.yml:22-68) stays on ubuntu-24.04 and windows-2025. It gains the steps
  "CI image inputs tests" and "CI image check tests" (T1, T2), next to
  `tests/ci/test_check_vulkan_device.cmake` (ci.yml:47-48).
- **tools gains a Linux-only step "CI image pin"**, with `timeout-minutes: 10`. It reads `DVV_CI_IMAGE`
  from dvv-ci.yml and then checks three things, with an empty `DOCKER_CONFIG`, so anonymously:
  1. `docker buildx imagetools inspect` of the pinned digest succeeds, so the package is public and
     the digest exists.
  2. Its `dvv.ci-image.inputs` label equals `tools/ci-image-inputs.cmake` of this commit.
  3. The tag `inputs-<h16>` points to the same digest, so the pin is the published image of these
     inputs and not a hand-pushed one.

  Every dvv-build PR and main run carries this step, so no unpublished, private or mismatched pin
  can be merged or tagged.

## 7. Measuring the speed-up

The numbers go in the dvv-build PR description, as a table:
- **Before:** the last five green runs on dvv-build 0.5.0 of dvv-base (lib) and rawreel (app), and
  the self CI.
- **After:** five runs of the same repositories on the 0.5.1 branch (`@feat/…`, §9).
- The first, cold-prime run of each repository is listed apart and not counted.
- Durations come from `gh run view <id> --json jobs` (each step's start and end).

| What | Before | After |
|---|---|---|
| Per Linux job (prime-linux on a cache hit, linux-clang, -asan, -tsan, lint, tidy): wall time, median and max | | |
| Install time per job: apt steps, setup-python and Install tools (before) vs "Initialize containers" (after), median and max | | |
| Whole run: first job start to last Linux job done, median | | |
| Image: compressed size, the layer count, and the pull time inside "Initialize containers" | n/a | |
| `df -h /` at the end of linux-clang-asan with `test-dependencies` (rawreel) | | |
| Hangs over 5 minutes, and reruns needed, in the window | the brief's evidence: hangs of 12-21 min, 6 reruns in one PR | |

**Decision rule.** No Linux job's median wall time may be worse than before.
- Expected risk: lint, and prime-linux on a full cache hit. Both trade a few seconds of tool-cache
  Python and wheels for a pull of the whole image.
- If lint is slower, lint goes back to the host with setup-python and a pip install with retries
  (§5.9 style).
- If another job is slower, the image is slimmed or the layer compression changes (V13) before the
  merge.
- Free disk at the end must stay above 10 GB, or the image is slimmed.

The PR also states which steps are gone and that no Linux job contacts an Ubuntu mirror or PyPI.
`grep -n 'apt-get\|setup-python\|pip install' dvv-ci.yml` shows only Windows and macOS lines.

## 10. Decisions (confirmed by the user, 2026-11-19)

The user confirmed all four as recommended.

- **Q1. Make the GHCR image public.** Recommendation: public. Each job's pull logs in with the
  caller's token, which has no package scope, so a private image would need `packages: read` and a
  per-repository grant in every caller and would break 0.5.1's compatibility. Trade-off: anyone can
  pull the image, which holds only public Ubuntu packages and public wheels.
- **Q2. Run the container as the runner's non-root user, with Docker's limits relaxed** (`--user
  <runner uid:gid> --init --ipc=host --security-opt seccomp=unconfined`). Recommendation: yes. As
  root, the permission tests pass without checking. The options keep orphan reaping, shared memory
  and TSan's re-exec as on the host. Trade-off: weaker isolation inside a throw-away VM that already
  has passwordless sudo.
- **Q3. No apt fallback.** A failed image pull fails the job, and you rerun it. Recommendation: no
  fallback. Trade-off: a GHCR outage stops Linux CI until GitHub recovers. A fallback would keep an
  untested second environment and bring back the mirror hangs.
- **Q4. Freeze the Ubuntu packages at a snapshot, per dvv-build release.** Recommendation: yes. It
  makes the image reproducible and the cache keys exact. Trade-off: CI stops following noble-updates
  until the next image. rawreel's Linux release build, which still uses the live mirror, can differ
  until it adopts the image (follow-up issue).

The spec's own calls are listed for the reviewers, not for the user:
- setup-python's Python build and environment (§5.2)
- lint moves into the image, subject to the §7 rule (§5.4)
- the owner comes from `job.workflow_repository`, with a fork variable (§5.4)
- one set of options for every Linux job (§5.5)
- the full check runs on every job (§5.6)
- the environment hash goes into the Linux keys (§5.7)
- brew ninja is deleted (§5.9)
- no attestations and no release tag on the image (§5.3)
- the tools job stays on the host (§5.10)
- the version is a patch (§9)

## 14. Revision 3: plan-review errata

From the reviews of the implementation plan (A-I2, B-C1, B-M8, B-M14). §10's four decisions are
unchanged.
- §5.2: setup.sh's unpinned pip upgrade is pinned. The new `ARG PIP_VERSION` holds the pip that
  ensurepip bundles with `PYTHON_VERSION`. `PIP_CONSTRAINT` makes setup.sh's upgrade install exactly
  that pip, and the build fails unless `pip --version` reports it. `pip.lock` is `pip freeze --all`,
  so pip enters the environment hash. A new spec's-call bullet gives the reason.
- §5.2: the Python download runs in a `download` stage that installs curl from the snapshot. No
  package of the image provides a downloader, and curl stays out of the final image. The new
  `ARG PYTHON_URL` names the python-versions archive.
- §5.3 step 6: the tag is created with `imagetools create --prefer-index=false`. Without it, the tag
  names a new index and not the pushed manifest, so §5.10's pin check could never pass. The tag's
  digest is inspected and must equal the pushed digest.
- §5.6 item 5: the report prints `user <uid>:<gid> (workspace owner <uid>)`.
- §8 V9: the criterion adds `python -m pip --version` = `PIP_VERSION`.
- §8 V15 (new): the §5.3 publish flow (push by digest, tag, then inspect the tag and read the label
  anonymously) is proved on a real runner during the spike.
- §5.2 CA bootstrap: snapshot.ubuntu.com is HTTPS-only, and the bare base image has no CA bundle.
  So the throwaway download stage installs ca-certificates from the base image's own archive, whose
  packages apt checks by signature. The final stage's first group mounts that bundle until the image's
  own ca-certificates is installed. TLS verification stays on, and everything in the image comes from
  the snapshot.
- §5.2 machine-id: `/etc/machine-id` is the first 32 hex digits of `DVV_CI_IMAGE_INPUTS`, and
  `/var/lib/dbus/machine-id` links to it. This replaces the random id that a postinst writes, so the
  image is a function of its inputs.
- §5.5 / V10: the container options gain `--ulimit core=0:-1`, because the host's soft core limit is 0.
- §5.6 and §8 V9/V14: the four wheel tools are compared by `pip show` `Version:` exactly. Their
  `--version` is only an entry-point check. ninja's wheel prints `1.13.2.git.kitware.jobserver-pipe-1`,
  which passes as `<pin>` or `<pin>.git.…`.
- §5.3 publish: the workflow triggers on `branches: ['**']` with the path filter, so a tag push never
  runs it. The Look up step validates the digest. After the push, the workflow compares the pushed
  image's rootfs diff_ids with the checked local image's, so the check holds on both the classic and
  the containerd image store.
- §6 T7: the sanitizer test prints `unreadable` for a /proc file that it cannot read, which is
  mmap_rnd_bits for uid 1001.
- §5.3 / S1: only the logged-in `<ref>: not found` counts as absent. The "denied" message on a private
  package was inferred, not observed.
- 8. §5.1 inputs: ci-image.yml. The inputs hash also covers `.github/workflows/ci-image.yml`, as a
  required named input like `tools/requirements.txt` and the inputs script. Reason: tag squatting. The
  workflow decides how the image is built, so without it a workflow-only edit could create an
  `inputs-<h16>` tag for unchanged inputs, and a later honest build of those inputs would find the
  tag and reuse it. `tools/check-ci-image.cmake` stays out, because it builds nothing into the image.
  Cost: every edit to ci-image.yml changes the hash and rebuilds the image, and its digest has to be
  pinned again in dvv-ci.yml.

  to 42 s in dvv-base and 28.5 s to 46 s in rawreel, because pulling the container dominates a job
